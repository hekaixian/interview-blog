# 缓存
## 1、为什么使用redis，项目中如何使用的

主要是两点，高性能，可以将一些结果很少变动，但是查询数据库很耗时的查询，将结果放在缓存中，直接查缓存。高并发，大量的请求如果直接打到数据库，数据库承受不了，可以把数据放到缓存，redis的并发能力很强。

用户关联的家庭设备相关的信息，一般变动的频率不会很频繁，并且各个设备信息存储的比较分散，查询比较耗时，所以查出来直接存到缓存中。还有就是一些热点信息，会大量访问的，比如设备状态，推荐场景等，也放到缓存中，支持c端的大量访问。

## 2、redis的数据类型和使用场景

1. string，简单的key\-value结构

2. hash，类似map结构，可以存放对象，比如存放设备信息像id，名称，地址ip、功能配置这种

3. list，列表结构，有序列表，可以实现一个简单消息队列

4. set，无序集合，自动去重，可以做一些交集、并集的操作

5. sorted set，有序集合

## 3、redis缓存雪崩、缓存穿透、缓存击穿的区别和解决方法？

缓存雪崩：在同一时间内，大量缓存数据同时失效，大量请求直接打到数据库上。

方案：缓存数据设置不同的失效时间，使不同缓存数据的过期时间更加分散。

缓存击穿：对于一些热点数据，在缓存过期的瞬间，大量并发请求同时访问该数据，请求直接打到数据库。

方案：热点数据可以直接设置永不失效，加互斥锁。

缓存穿透：请求的数据在缓存中和数据库中都不存在，请求直接打到数据库。

方案：使用布隆过滤器，或者查询发现数据库不存在时，将这个key缓存一个较短过期时间的空值到缓存中。

## 4、缓存过期策略有哪些

定时删除，设置key的过期时间，创建一个定时器，到过期时间时，定时器执行堆该key的删除操作，使用比较少，cpu消耗比较高

惰性删除，key过期时不会立即删除，等下次访问该key时，如果过期了，就删除，并返回该值。

定期删除，没隔一段时间，redis随机抽取一定数量的key检查过期，然后删除。随机抽取是避免全量扫描，如果有几十万的key，太消耗性能

redis实际采用的时惰性删除和定期删除相结合的策略，平衡内存空间和cpu资源的使用。

## 5、定期\+惰性都没有删除过期的key怎么处理

当一个过期的key，在定期随机的时候没有被删除，这个key也没有被访问，就会堆积在内存中

redis有8种内存淘汰机制：

1. 在设置过期key或者所有key中，移除最近不常用的

2. 在设置过期key中，移除离过期时间最近的key

3. 在设置过期或者所有key中，随机移除key

## 6、redis事务机制

redis支持简单的事务，但是不支持回滚，而且原子性支持有限，事务存在部分执行的可能。

实现原理：基于multi、exec、discard、watch几个命令：

1. multi，开始事务，命令被放入一个队列

2. exec，执行事务，按照队列中的顺序执行，eg，如果执行过程报错，则部分事务会执行，不能保证原子性

3. discard，取消事务

4. watch，监视key值，通过乐观锁实现，在执行exec之前，如果被监视的健被其他客户端修改了，事务将被放弃，返回null

## 7、redis为什么比较快

- 基于内存实现，避免操作磁盘

- 高效的数据结构，哈希表，链表，跳表等

- 单线程模型，网络请求模块和数据操作模块使用单线程，因为redis是基于内存实现的，cpu不是性能瓶颈，并且多线程存在并发问题，线程切换也会带来一定开销

- 使用了I/O多路复用模型，使用epoll，在一个线程同时监听多个网络连接事件

- 集群和分布式架构，将数据分散存储在多个节点

## 8、redis的I/O处理线程模型

内部使用的是文件事件处理器，是单线程的，所以说redis是单线程的

它采用I/O多路复用模型，同时监听多个socket，将多个socket放入内存队列中，

事件分派器每次取出一个socket，根据socket的事件类型分配不同的事件处理器处理

## 9、redis6\.0为什么引入多线程

redis的性能瓶颈主要是网络I/O上，采用多线程使网络请求并发执行，

减少网络I/O等待，提升性能，而数据的读写操作还是单线程的，就避免了并发问题

## 10、redis有一亿个key，其中10万的key有相同的前缀开头，怎么查出来

使用keys命令，可以扫出指定模式的key列表

因为redis是单线程的，keys命令会导致redis阻塞一段时间

也可以使用scan命令无阻塞的取出，但是可能重复，可以取出来后再去重

## 11、redis的持久化机制

RDB持久化，隔一段时间将所有数据的快照以二进制文件的方式存在磁盘中。但是不能实时持久化；容灾性好，恢复速度快，但是不同版本的存在兼容问题

AOF持久化，当有修改数据的命令时，都会将该命令写到AOF文件的末尾。AOF文件大，恢复数据比较慢。AOF三种模式控制意外停机丢失的数据量：

always：总是写入

everySec：每一秒写入，默认模式

no：不主动写入，由操作系统决定什么时间将缓存中的命令写入磁盘

## 12、AOF重写是什么，为什么会阻塞主线程？

为了合理控制AOF文件的大小，AOF重写可以重新生成一个AOF文件，重写时会优化AOF文件中的命令，重新生成的AOF文件体积比较小。

redis使用的是AOF持久化，并且使用的是everySec模式，每秒写。这样导致在重写的时候，AOF持久化被阻塞。可以将no\-appendfsync\-on\-rewrite设置为yes，重写的时候不持久化。

## 13、redis主从复制原理

1. 主从同步机制：第一次同步时，主节点做一次bgsave持久化，同时将后续的修改操作记录到缓存中，等RDB文件生成后全量复制到从节点，从节点将RDB镜像加载到内存。加载完成后，主节点将缓存中的修改操作记录同步到从节点执行，后续的增量通过AOF文件同步。

2. 主从复制的步骤：是从节点发起的，有3种方式，配置文件、启动命令、客户端命令

## 14、缓存和数据库数据一致性怎么保证？

旁路缓存模式，写：先更新数据库，再删除缓存；读：先读缓存，有就返回，没有就读数据库，并更新到缓存

问题1：如果更新数据库后，缓存删除失败了，缓存中还是旧数据

优化：写：先删除缓存，再更新数据库

问题2：那如果先删除缓存，数据库还没更新，又一个其他请求，读缓存没有，读数据库，拿到旧值，有写到缓存，后面数据库才更新完成，有会导致不一致

优化：使用队列，根据资源的唯一id，将更新数据库操作放到jvm内部队列中，如果有同一资源的其他查询请求进来，将读库，写缓存操作也放到队列中，队列中的操作串行执行

## 15、大key怎么处理

通过bigKeys找出大key

（1）拆分大key，如字符串类型的根据业务逻辑拆分多个小字符串key

（2）异步处理，用消息队列来异步处理大key，避免阻塞主线程

（3）定期清理，设置合理的过期时间

（4）合理的升级redis服务器的硬件配置

（5）从业务逻辑上优化，避免生成大key

## 16、redis集群的使用

Redis Cluster（扩死特儿） 是 Redis 的分布式解决方案，五主五从，至少需要3个物理节点

1. 无中心结构，多个redis节点组成，节点间通过gossip通信，一个redis cluster至少需要3个主节点。

2. redis cluster使用哈希槽做数据分片，有16384个哈希槽，每个主节点负责一部分哈希槽，存储和获取数据，会根据key的哈希值对16384取模，得到槽编号，根据哈希槽和节点映射关系，将请求路由到负责该哈希槽的节点上

3. gossip节点通信：meet消息，节点加入时，通知其他节点。ping消息：定期发送，检查节点的可达性和交换节点信息。pong消息：meet和ping的响应。fall：当一个节点认为另一个节点下线时，通知其他节点。

4. 高可用和故障转移，节点间定期发送ping消息检查彼此可达性，如果一个节点没有收到另一个节点的响应，将其标记为疑似下线，当有足够多的节点都认为某个节点疑似下线时，会将其标记为已下线。当一个主节点被标记为已下线时，它的从节点会发起选举，选出一个新的主节点来接管。选举过程基于Raft算法

## 17、分布式缓存寻址算法

1. hash算法：对key值进行hash运算，运算结果对分片数取模，定位分片

2. 一致性hash算法

3. redis cluster的hash solt算法

## 18、多级缓存中，本地缓存和分布式缓存如何保持一致

分布式缓存一般是redis缓存，本地缓存是保存在各个服务器上的缓存，

使用消息队列，删除redis缓存时向队列发送一个消息，服务器消费者消息删除本地缓存
