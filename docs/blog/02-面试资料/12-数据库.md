# 数据库
## 1、MySQL和MongoDB有什么优缺点？

mysql优点：支持事务，关系模型强大，成熟稳定，sql支持，数据一致性

缺点：扩展性有限，不适合非结构化数据，性能存在瓶颈

mongoDB优点：支持文档型数据库（json），高扩展性，高并发读写性能好，灵活的数据模型动态添加、修改字段，分布式架构

缺点：事务支持有限，多表联查查询能力弱，

## 2、做项目时数据库选型是怎么选的？

MySQL适用于对数据一致性要求高，并且需要处理事务的场景

mongoDB适用于处理大量非结构化嵌套类型数据的项目，json类型

## 3、数据库做分库分表，怎么解决数据清洗问题？

分库分表时，怎么实现数据迁移和清理?

一、设计思想：

1\.全量迁移，增量同步双重保险；

2\.按照分片逐步切流量验证，支持快速回滚。

二、具体策略

1\.使用用户表的userId作为分片健，通过hash分片，分片号=hash\(userId\)% 128；将用户表分为4个库，每个库32个表。

2\.使用ShardingSphere\-Proxy作为分库分表中间件，按分片规则将数据分布到新库表，最后再验证全量数据一致性。

3\.写、修改操作写入旧表后通过Binlog异步同步到新表，使用Canal监听旧表Binlog，解析Binlog事件，按分片规则写入新表。

5\.灰度流量切换，按照分片号逐步切换，每个分片验证通过后，再切换下一个分片，其中读写分离，先切读请求到新表，验证没问题，再切写请求。

6\.旧表保留3个月，方便回滚，3个月后没有问题了，再关闭流量，删除数据。

7\.切流量的过程中，时刻要监控服务，要每天对比新旧表的数据一致性问题，还有慢sql问题等。

## 4、分库分表的策略是什么，怎么分表的？

垂直方向：

按业务功能划分，不同的业务，将相关的表放在不同是数据库中。按照字段使用频率或者类型划分表的字段，常用字段放一个表，其他字段放另一个表。

水平方向：

按照范围划分，比如按照用户id或者时间范围，将数据存放在不同的库和表，通过hash取模的方式划分，一般对id取模。

## 5、分库分表后，关联查询问题怎么解决

1. 全局表，对一些各个库都依赖的数据字典表，每个数据库都复制一份。

2. 字典冗余，用空间换时间，对一些关联查询其他数据库的字段，可以冗余在表中

3. 使用ShardingSphere，配置好分库分表规则，它会将普通的查询sql自动处理成分库分表逻辑

4. 分多次查询，在代码层面组装数据

### 1、三层架构

1. 连接/线程处理：mysql服务器上有一个线程池，客户端连接服务器时会验证，分配一个线程

2. 解析查询：先查询缓存，如果有相同sql的查询结果则直接返回，没有的话，就通过解析器解析sql，然后通过优化器按照最小消耗来优化，返回查询结果的同时，也缓存下来

3. 存储引擎：存储数据、提取数据，开启事务，存储引擎通过API和上层通信，屏蔽了不同引擎之间的差异

### 3、索引原理

基础分类：

1. 主键索引：一个表只有一个主键索引，主键索引的值不能为null，主键索引可以作为外键

2. 唯一索引：可以多个唯一索引，值可以为null，不能作为外键

3. 普通索引

4. 组合索引（联合索引）：多列组合构建的索引，遵循最左原则

5. 全文索引：对大文本建立索引

数据结构：

1. 哈希表：key\-value的结构，哈希冲突会形成链表，适合于等值查询

2. 有序数组：使用于静态存储引擎，数据不会改变，等值和范围查询性能高

3. B\-Tree：多路平衡查找树，节点中包含数据信息

4. B\+Tree：非叶子节点中值存储键值信息，数据信息存储在叶子节点，所有叶子节点之间有一个链指针

物理存储：

1. 聚族索引：InnoDB

2. 非聚族索引：MyISAM

### 4、索引使用原则

1. 查询频率比较高的字段使用索引

2. 区分度底的字段，如性别，不要用索引，离散度太低

3. 组合索引要遵循最左原则，查询频率高和离散度高的字段放在最左边

4. 频繁更新的值不要作为主键或者索引

5. 不建议无序的值作为主键索引

6. 不要过度索引，索引也会占用空间和性能

7. 如果字段值太长，可以使用短索引

### 5、索引失效情况

1. where条件中使用了计算函数

2. 查询字符串时不加引号，发生隐式转换

3. 组合索引查询时没有遵循最左原则

4. like条件中字符串开头带%

5. 像not like这种负向查询

6. or连接多个查询条件，且其中一个条件不带索引，则整个查询索引失效

### 6、怎么避免死锁

1. 减少事务持有锁的时间，将不必要的操作放在事务外部执行

2. 优化查询和索引

3. 按照顺序访问资源，线程1访问顺序是表A\-表B，则线程2最好也是

4. 尽量使用行级锁

5. 监控和处理死锁，设置死锁等待超时时间

### 7、深度分页怎么优化

利用索引覆盖，如果只查询少量字段，创建覆盖索引优化深度查询。

子查询结合索引：使用子查询先获取需要的主键，在通过主键关联查询完整的数据。记录上上一次查询的最后一条记录的主键值，下次查询直接从该主键值之后开始查询，避免使用offset偏移量。

### 8、order by怎么优化

如果数据本身是有序的，可以使用联合索引

参数优化，调整排序内存大小，在内存中排序比较快，调整排序数据最大长度，避免rowid排序，要回表。

### 9、执行计划

explan，

id：查询的唯一标识符，id相同，执行顺序从上到下，不同，大的先执行。

type访问类型，一般优化为range比较好，就是只检索给定范围的行，使用一个索引来选择行。

key：实际使用的索引

### 10、sql执行过程

先检查缓存中是否存在该查询，存在，则直接返回结果

对sql进行解析、语法检查和于处理，然后给优化器优化之后生成执行计划

执行器根据执行计划从存储引擎中获取结果返回

### 11、sql优化

（1）sql语句优化

1\.索引失效的情况要避免

2\.不要使用select \*，是全表扫描

3\.条件中不要使用null判断，最好有默认值

4\.分页优化，深度分页使用覆盖索引或者子查询加索引

5\.使用join的时候要小表驱动大表，join条件要正确，避免笛卡尔积

6\.子查询中可以把in改为exists

（2）数据库配置调优

InnoDB缓冲池配置、连接池的配置、日志和持久化平衡

（3）表结构优化

1\.大表可以分库分表，

2\.配置读写分离，

3\.热点数据使用缓存

### 12、MySQL内存溢出怎么排查和解决

1. 检查MySQL配置参数，主要是内存相关的参数，比如缓冲池的大小等，根据物理内存设置合适大小，太大可以内存溢出

2. 分析MySQL进程内存使用情况，使用top或者htop名称，查看进程占用的内存情况，使用ps查看更详细的进程信息

3. 查看MySQL的错误日志和慢查询日志，看下具体的错误原因或者有哪些慢sql

4. 对于频繁查询的sql，使用explain分析是否存在全表扫描或者索引未使用情况

5. 检查是否存在长事务，将长事务拆分多个短事务

6. 即时清理数据库中无用的垃圾数据
